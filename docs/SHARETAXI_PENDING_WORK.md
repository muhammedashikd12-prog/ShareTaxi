# ShareTaxi.co Pending Work Audit

Audit date: 2026-10-19

## Scope and evidence

This report reflects the current checkout, not assumptions from earlier summaries. The repository contains an Expo Router mobile prototype, a Next.js website with one implemented route, two small shared packages, and an empty `supabase/` directory. There is no `apps/web/src/app/admin` route or other admin dashboard, backend implementation, native `android/` or `ios/` project, EAS configuration, CI workflow, or environment template. The root Git repository has no commits and reports its project files as untracked; this audit did not modify application source or the website.

Verified in this checkout:

- `npm run typecheck:mobile` — passed.
- `npm run test --workspace apps/mobile` — passed; one suite, six tests, covering mock booking lifecycle and commute preference helpers.
- `npm run typecheck --workspace apps/web` — passed.
- `npm run lint --workspace apps/web` — passed.
- `npm run build --workspace apps/web` — passed; Next.js generated only `/` and `/_not-found`.
- `npm run build:mobile` — passed; Expo web export.
- `npx expo export --platform android --clear` from `apps/mobile` — passed; Android JS bundle export.
- Native smoke test — passed on `ShareTaxi_Medium_API_36_Recovery` with Expo Go 58.0.4. ADB confirmed Android boot completion and system services. ShareTaxi rendered; onboarding, Home, and Intercity search were opened with device input and checked by screenshot/UI hierarchy. Android logcat showed `ReactNativeJS: Running "main"` with no fatal or unhandled JS exception during this smoke test.

The original `Medium_Phone_API_36.0` AVD remains broken. A normal reboot and a cold boot still reproduced SystemServer/PackageManager failure while reading its persisted permission-state file. It was preserved and not wiped. The healthy recovery AVD is a separate device.

The complete native booking, on-demand, commute, settings, and profile journeys were **not** tapped through. The browser-flow results recorded in [MOBILE_PROJECT_STATUS.md](./MOBILE_PROJECT_STATUS.md) are browser verification, not native Android verification.

### Priority and ordering

`P0` is a prerequisite/blocker; `P1` is core product foundation; `P2` is product capability; `P3` is release/hardening. Numbers indicate the recommended dependency order, not a commitment to build every feature. Keep real dispatch and payments disabled until their respective safety, legal, operational, and security acceptance criteria are met.

## Recommended implementation order

1. **P0 — Finish manual native E2E on the healthy recovery emulator**; test booking, on-demand, commute, tabs/settings/profile, keyboard, modal sizing, and back behavior. Keep browser and Android evidence clearly separated.
2. **P1 — Resolve product truth and domain contract.** Correct the README's admin claim; decide which three ride modes are launch scope; define rider/driver/admin roles, trip/booking/status/inventory rules, cancellation/refund policy, safety process, and supported geography. Remove/rephrase nonexistent emergency-button guidance.
3. **P1 — Build backend/database/API and auth.** Add migrations, secure configuration, server-side authorization/validation, persistent user/driver/trip/booking/commute records, atomic seat inventory, integration tests, and staging.
4. **P1/P2 — Complete intercity first; then driver workflows and admin operations.** Wire mobile/web clients to the same source of truth, implement driver supply and safe operations, then real on-demand matching only when operational support exists. Implement full commute schedule and persistence.
5. **P2 — Add maps/location, notifications, and payments only as separately scoped integrations.** Do privacy/safety review before location or emergency capabilities; do provider/legal/compliance work before payments; keep all disabled until independently tested and approved.
6. **P2/P3 — Security and quality gates.** Threat model, authorization tests, accessibility/native QA across Android and iOS, dependency/build checks, observability, backups, incident response, and formal security review.
7. **P3 — Deployment and release readiness.** Establish CI, staging/production environments, EAS signing and store builds, website hosting, rollback, policy/store assets, and launch acceptance review.

## Highest-priority five tasks

1. **Complete native Android E2E on `ShareTaxi_Medium_API_36_Recovery`**; only onboarding/Home/Intercity search have been tapped on Android so far.
2. **Choose and document authoritative ride-domain rules**, including how trips, seat inventory, cancellations, recurring commutes, and all three ride modes should behave.

4. **Implement real authentication and server-side role/authorization controls** before storing personal or driver data.
5. **Build the operational foundations for supply and oversight**: driver workflows first, then protected admin moderation/support. Do not enable live on-demand dispatch before these exist.
